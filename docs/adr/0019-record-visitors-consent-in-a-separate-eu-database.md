# ADR 0019: Record visitors' consent in a separate EU database

- Status: Accepted
- Date: 2026-10-22

## Context

This is the delegated decision
[gq-platform ADR 0008](https://github.com/Quick-Release/gq-platform/blob/claude/cookie-consent-foundation/docs/adr/0008-consent-and-legal-pages.md)
asks the Blueprint to record beside [ADR 0003](0003-serve-published-content-from-a-durable-store.md).
ADR 0008 is itself **Proposed**: this was implemented under the Platform
decision owner's directed execution batch, ahead of its acceptance, and is to
be revisited if ADR 0008 is amended or rejected.

CONSENT-1 (gq-platform's consent baseline, Proposed) requires each visitor
decision to be recorded through a same-origin endpoint on the Site's own
Frontend Worker, into a consent database per Site and stage that is created
in the EU and kept apart from the publication store (CN-R8 to CN-R11).
gq-content's consent Runtime (`@getquick/content/consent*`) owns the
endpoints, the record schema, its migrations and the purge; it can't create
the database or choose where it lives. The Blueprint provisions everything a
Frontend deploys with, so that falls here.

It is the first store a visitor's request writes. ADR 0003's publication
store is written only by a trusted refresh: "a visitor request reads only the
store; it never reads the CMS and never writes."

Facts checked against the pinned stack (Alchemy 2.0.0-beta.79):

- `Cloudflare.D1.Database` takes `jurisdiction` (`"eu"`); Cloudflare sets it
  at creation and can't change it, and Alchemy replaces a database whose
  declared jurisdiction differs. Cloudflare's D1 listing reports each
  database's `jurisdiction` (null for none).
- `Cloudflare.RateLimit` is a Worker binding with no cloud resource; its
  `namespaceId` scopes the counters.
- A Worker's `crons` need a `scheduled` handler in its entry. The Astro
  Website's Worker entry (`@alchemy.run/frontend-frameworks`) exports `fetch`
  only, so a content Frontend can't run a cron itself.

## Decision

- **A second, visitor-writable database, in the EU.** Each Site and stage
  gets `<project>-fe-consent[-<stage>]`, declared in the managed
  `infra/consent.ts`, created with `jurisdiction: "eu"`, migrated from the
  consent Runtime's `consentMigrationsDirectory` and bound as `CONSENT_DB`.
  Production's is retained like the publication store. Only the consent
  Runtime's record endpoint writes it, append-only.
- **The publication store's guarantees are unchanged.** Visitors still never
  write `PUBLICATION_DB`; nothing consent-related is stored there or read
  from it. The consent database holds no published content and isn't a
  source for any page.
- **Opt-in by the Frontend.** The consent database, its bindings and its
  purge exist only when `apps/frontend` has a consent Runtime installed
  (`@getquick/content` exporting `./consent/migrations`). A Frontend without
  one deploys as before. This mirrors ADR 0003's opt-in by migrations.
- **Its credentials and limits.** `CONSENT_READ_TOKEN`, generated by
  `gq frontend secrets` like the Frontend's other secrets and held in Sigillo
  staging, is bound to the Worker as a secret and written to the CMS's
  `.env` as `GETQUICK_CONSENT_READ_TOKEN` by `gq ploi events`, beside
  `GETQUICK_FRONTEND_URL`, the only origin GQ Config sends it to.
  `CONSENT_RATE_LIMITER` (30 a minute per client IP, per Site and stage) is
  bound to the Worker; the IP is never stored.
- **The purge runs in a Worker of its own.** `<project>-consent-purge[-<stage>]`
  binds the same database and runs daily on a cron trigger, with no public
  URL, named outside the `<project>-fe-<stage>` pattern that offboarding reads
  as a Frontend stage. Its entry, the managed `apps/frontend/workers/consent-purge.ts`, only
  calls the consent Runtime's `purge()`: retention stays the Runtime's. One
  Worker for both variants, whatever the Frontend's framework exports.
- **Its location is checked.** `gq doctor` fails on any of the Site's
  consent databases outside `eu`, since Cloudflare can't move one.
  `gq site check` fails when GQ Config switches an optional service on
  (GA4) without the consent Runtime, when a public page loads from a host
  outside the Site, or when GQ Config's Legal Contract lacks a required
  legal page or the data controller.

## Considered options

- **Records in the publication database.** Breaks ADR 0003's guarantee and
  mixes personal-data retention with public content; rejected by ADR 0008.
- **Purging from the Frontend Worker's own cron.** Astro's Worker can't take
  a `scheduled` handler without replacing the adapter's entry; a TanStack
  Frontend could, but the variants would differ.
- **Purging from the CMS's server cron through an HTTP endpoint.** The
  Runtime has no purge endpoint, and it would put the CMS on the records'
  retention path; ADR 0008 keeps records out of WordPress.
- **Creating the database always, whatever the Frontend.** Every Site would
  hold an empty personal-data store it can't use.

## Consequences

- A visitor's decision is written to D1 on the request path. The publication
  store and its ADRs (0003 to 0013) are untouched.
- A consent database created outside the EU can only be replaced: export its
  records, delete it, redeploy and import them ([consent guide](../guides/consent.md)).
- A Site whose controller sets a shorter retention than the Runtime's default
  needs it passed to the purge too; the purge Worker uses the default today.
- Offboarding ([ADR 0011](0011-offboard-a-site-by-cutting-access-before-archiving.md))
  archives each stage's consent database (`consent[-<stage>].sql`) with the
  rest of the Site, then deletes its purge Worker and the database. The
  archive then holds visitors' consent records, the controller's proof of
  consent: CONSENT-1's retention (CN-R10) governs how long it keeps them.
