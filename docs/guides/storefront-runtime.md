# Add the storefront Runtime to a commerce Site

[Documentation](../README.md)

A commerce Site's catalog, cart, checkout and customer sign-in come from the
storefront Runtime, `@quick-release/storefront`, mounted behind its Frontend's
Worker at `/api/store/*` and `/api/auth/*`: a same-origin BFF to WooCommerce's
Store API and GQ eCommerce's customer auth
([ADR 0017](https://github.com/Quick-Release/gq-site/blob/main/docs/adr/0017-generate-commerce-sites-from-the-variant-alone.md)).

`gq new --variant commerce` mounts it from `@getquick/site` 0.29.0. A Site
generated by 0.28.0 has a Frontend without it, and `gq sync` never adds it:
everything in `apps/frontend` is the Site's own. This guide adds it by hand,
to the same shape a new Site gets. Mounting it doesn't make the Site ready:
`gq site check` does, once a cart round-trips through the Worker and the
other checks pass ([Readiness](commerce-sites.md#readiness)).

## Before you start

- Bump `@getquick/site` to 0.29.0 or later and run `gq sync`. That brings the
  managed deploy (`infra/frontend.run.ts`, `infra/storefront-bindings.ts`,
  `infra/scripts/deploy-frontend.mjs`) and the Cloudflare CI Worker that
  installs private packages and hands the storefront's secrets to the
  Frontend's deploy (`infra/ci/cloudflare.ci.ts`, `infra/ci/env.ts`).
- Keep a GitHub token with `read:packages` in your **user-level** npm config,
  never the repository's (pnpm ignores tokens there, and the generated
  `.npmrc` only names the registry):

  ```sh
  npm config set --location=user //npm.pkg.github.com/:_authToken <token>
  pnpm view @quick-release/storefront version   # 0.2.2 or later: you can read it
  ```

  The token's owner must be able to read the `@quick-release/storefront` and
  `@quick-release/auth-contract` packages in the Quick-Release organization.

## 1. Depend on it

Pin the Runtime and the auth contract exactly; both are on GitHub Packages
and nothing comes from Ekis:

```sh
pnpm --dir apps/frontend add --save-exact @quick-release/storefront@0.2.2 @quick-release/auth-contract@0.1.9
pnpm --dir apps/frontend add @tanstack/react-query@^5.105.0
pnpm --dir apps/frontend add -D --save-exact @cloudflare/workers-types@5.20261026.1
```

Add `"@cloudflare/workers-types"` to `compilerOptions.types` in
`apps/frontend/tsconfig.json`, and keep `cloudflare:workers` out of the bundle
in `apps/frontend/vite.config.ts` (it exists only in workerd):

```ts
build: { sourcemap: true, rolldownOptions: { external: ["cloudflare:workers"] } },
```

## 2. Configure it for the Site

`apps/frontend/src/storefront.server.ts` says which Site the Runtime serves,
from `gq.ops.json`, and reads the Worker's bindings:

```ts
import "@tanstack/react-start/server-only";
import {
  createStorefrontRuntime,
  type StorefrontBindings,
  type StorefrontRuntime,
} from "@quick-release/storefront/server";

import ops from "../../../gq.ops.json";

const domains = (ops as { domains?: { admin: string; frontend: string } }).domains;
const ddevProject = "<project>-admin"; // apps/cms/.ddev/config.yaml name
const local = import.meta.env.DEV || !domains;
const storefrontUrl = local ? "http://localhost:3000" : `https://${domains.frontend}`;
const cms = local ? `https://${ddevProject}.ddev.site` : `https://${domains.admin}`;

async function bindings(): Promise<StorefrontBindings> {
  const workers = await import("cloudflare:workers").catch(() => null);
  return (workers?.env ?? {}) as StorefrontBindings;
}

let runtime: Promise<StorefrontRuntime> | undefined;

export function storefront(): Promise<StorefrontRuntime> {
  runtime ??= bindings().then((env) =>
    createStorefrontRuntime({
      env,
      storefrontUrl,
      storeApiUrl: `${cms}/wp-json/wc/store/v1`,
      wordpressApiUrl: `${cms}/wp-json/`,
    }),
  );
  return runtime;
}
```

`storefrontUrl` is the public origin cart handles are bound to; the Store
API and WordPress API URLs must share the CMS's origin.

## 3. Mount it

Two server routes hand every request under them to the Runtime, which answers
a method it doesn't serve with a 405 rather than the page.
`apps/frontend/src/routes/api.store.$.ts`:

```ts
import { createFileRoute } from "@tanstack/react-router";

import { storefront } from "../storefront.server";

const handle = async ({ request }: { request: Request }) =>
  (await storefront()).handleStoreApiRequest(request);

export const Route = createFileRoute("/api/store/$")({
  server: {
    handlers: {
      GET: handle,
      POST: handle,
      PUT: handle,
      PATCH: handle,
      DELETE: handle,
      OPTIONS: handle,
      HEAD: handle,
    },
  },
});
```

and `apps/frontend/src/routes/api.auth.$.ts`, the same with
`createFileRoute("/api/auth/$")` and `handleAuthRequest`.

## 4. Give the router the Query client

The Runtime's client calls (`@quick-release/storefront/client`) run on its
Query client, which keeps cart and session queries private. Make one per
router, so no request's state reaches another, in `apps/frontend/src/router.tsx`:

```tsx
import { createStorefrontQueryClient } from "@quick-release/storefront/client";
import { QueryClientProvider } from "@tanstack/react-query";
import { createRouter } from "@tanstack/react-router";

import { routeTree } from "./routeTree.gen";

export function getRouter() {
  const queryClient = createStorefrontQueryClient();
  return createRouter({
    routeTree,
    context: { queryClient },
    scrollRestoration: true,
    Wrap: ({ children }) => (
      <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
    ),
  });
}
```

and type the context in `apps/frontend/src/routes/__root.tsx`:

```tsx
import type { QueryClient } from "@tanstack/react-query";
import { createRootRouteWithContext } from "@tanstack/react-router";

export const Route = createRootRouteWithContext<{ queryClient: QueryClient }>()({
  // head and component as before
});
```

Run `pnpm build` once: the TanStack Start plugin adds both routes to
`src/routeTree.gen.ts`, which you commit.

## 5. Check it

```sh
pnpm install --frozen-lockfile   # after committing pnpm-lock.yaml
pnpm verify
```

`pnpm-lock.yaml` must resolve every `@quick-release` package from
`npm.pkg.github.com`, with no git or Ekis path. Locally, `vp dev` and the
built server run outside workerd, so they have no bindings: `/api/store/*`
and `/api/auth/*` answer the Runtime's own 503 (`getquick_store_unavailable`,
`getquick_auth_unavailable`), which shows they are mounted.

## 6. Before the next deploy

With the Runtime installed, the managed deploy reads its `infra.json` and
binds what it lists: the `CART_SESSIONS` D1 database (retained in
production, its migrations applied before the Worker), the three auth rate
limiters, the secrets and the variables. It refuses to run, naming each one
missing, until the Site has:

- **Rate-limit namespaces** in `gq.ops.json`
  `cloudflare.rateLimitNamespaces` (`AUTH_IDENTIFIER_RATE_LIMITER`,
  `AUTH_IP_RATE_LIMITER`, `AUTH_PENALTY_RATE_LIMITER`), unused IDs from the
  [fleet's register](../reference/rate-limit-namespaces.md); see
  [Commerce sites](commerce-sites.md#rate-limit-namespaces).
- **Secrets** in Sigillo staging: `pnpm frontend:secrets` generates
  `GETQUICK_STOREFRONT_PROXY_SECRET`, `GETQUICK_AUTH_COOKIE_SECRET` and
  `GETQUICK_CART_SESSION_SECRET`. `TURNSTILE_SECRET` (from Cloudflare) is
  needed only once customer sign-in is enabled.
- **The CMS's proxy secret:** `pnpm ploi:provision` writes the same
  `GETQUICK_STOREFRONT_PROXY_SECRET` into the CMS's `.env`, where GQ
  eCommerce reads it.
- **`domains.admin`** in `gq.ops.json`, from which the deploy sets
  `GETQUICK_AUTH_UPSTREAM_URL`.
- **CI's packages token:** a `read:packages` token as `GITHUB_PACKAGES_TOKEN`
  in Sigillo staging, then `pnpm ci:deploy`. CI's install step writes it to
  the container's user-level npm config, and refuses with that instruction
  without it; the release step hands the storefront's secrets to the
  Frontend's deploy.
