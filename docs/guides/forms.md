# Headless Gravity Forms

[Documentation](../README.md)

A content Site whose CMS runs Gravity Forms can show its forms on the Frontend
and send them back to Gravity Forms, without loading anything from the CMS in
the visitor's browser
([gq-platform ADR 0009](https://github.com/Quick-Release/gq-platform/blob/main/docs/adr/0009-headless-gravity-forms.md)).
The capability is gq-content's, from 0.4.0: the CMS plugin
`getquick/gq-content` publishes each form's public descriptor with the pages
that reference it, and `@getquick/content` renders the form
(`@getquick/content/forms/astro`) and handles its posts
(`@getquick/content/forms/server`). The package's README documents both.

The Blueprint wires it into a Site that asks for it:

- `gq.ops.json` `forms` declares the provider and the spam controls the Site
  relies on.
- `gq sync` writes the managed route `apps/frontend/src/pages/gq/forms/[...rest].ts`,
  which hands `POST /gq/forms/<id>` to `createFormsServer`. Without `forms`,
  `gq sync` writes no form route.
- The Frontend's deploy binds what the route needs: a rate limiter, and
  Turnstile's keys when the Site chose Turnstile.
- `gq doctor` and `gq site check` check the Site's forms.

The Site keeps the rest. It chooses Gravity Forms and installs it, builds its
forms in WordPress, renders `gravityforms/form` blocks in its own block
dispatcher, styles them and chooses its spam controls. Reading entries, such
as charting survey answers, is the Site's own work: the capability has no
entry access and declares no credential for it.

## What a form can hold

The handler supports text, paragraph, email, phone, number, website, drop
down, radio buttons, checkboxes, consent, name, hidden, HTML and section
fields. Gravity Forms' own CAPTCHA, file uploads, payment and pricing fields,
page breaks, conditional logic, login-only forms and radio buttons with an
"Other" choice are not supported. A form that references one fails readiness
instead of rendering a form that can't be sent: replace the field, or take the
form off the page. Use Turnstile, not the CAPTCHA field, for a challenge.

## Adopting forms on a Site

The Site must be on the content package pair (`"contentRuntime": "package"`,
[The content runtime](sites.md#the-content-runtime)).

1. **Upgrade.** Set `@getquick/site` to `0.24.0` or later in the root
   `package.json`, run `pnpm install`, then `pnpm exec gq sync`. Sync pins
   `getquick/gq-content` and `@getquick/content` to exactly `0.4.0`. Then
   `pnpm install` again, and in `apps/cms` run
   `composer update getquick/gq-content`. A Site whose CMS was created before
   `@getquick/site` 0.24.1 also opens its REST gate to submissions
   ([The CMS's REST gate](#the-cmss-rest-gate)).
2. **Install Gravity Forms in the CMS** (`apps/cms/composer.json`, from the
   registry the Site already uses for it) and add `gravityforms` to
   `gq.ops.json` `wordpress.plugins`, so the CMS deploy activates it.
3. **Declare forms** in `gq.ops.json`:

   ```json
   { "forms": { "provider": "gravityforms", "spam": ["honeypot"] } }
   ```

   `spam` lists the controls the Site relies on: `"honeypot"` (Gravity
   Forms' anti-spam honeypot, enabled in each form's settings) and
   `"turnstile"` (Cloudflare Turnstile, verified by the Frontend). The
   handler always applies a form's honeypot when the form enables it, and
   Gravity Forms runs its own spam checks, such as Akismet, on every
   submission. No control is required. Then run `pnpm exec gq sync`: it
   writes the form route.

4. **Read the forms with the pages.** In `apps/frontend/src/lib/content.ts`,
   pass `forms: true` to `createContentRuntime`. Sites generated by 0.24.0
   or later already pass `forms: Boolean(manifest.forms)`. Without it, pages
   carry no descriptors, so no form renders and every post is refused.
5. **Render the block.** Hand `gravityforms/form` to `renderGravityForm` in the
   Site's block dispatcher (see [Rendering](#rendering)), and style the
   `gq-form*` classes with the Site's tokens.
6. **Turnstile, if the Site chose it.** See [Turnstile](#turnstile).
7. **Check.** `pnpm doctor`, then `pnpm site:check:local` with the local CMS
   running; see [Readiness](#readiness).
8. **Release the CMS and the Frontend together**, then refresh the Site
   (`pnpm frontend:refresh`) so every page is stored with its forms' descriptors.
   After that, saving a form in WordPress republishes every page that shows it.
   Send a test submission from each form page, and confirm that its entry and
   notification arrive in Gravity Forms.

To stop using forms, remove `forms` from `gq.ops.json` and run `gq sync`: it
removes the form route if the Site hasn't edited it. An edited route is left
in place for the Site to delete. Then remove `forms: true` and the block's
renderer.

## Rendering

`@getquick/content/forms/astro` renders a `gravityforms/form` block as a plain
HTML form that posts to `/gq/forms/<id>` and works without JavaScript. After a
post, the handler redirects back to the page, and the page shows the result.
A sketch, for a Site that renders a page's blocks with `renderDesignPattern`
(a `DesignBlock[]`) and its `blocks` option. A Site with its own dispatcher,
such as a `WpBlock.astro`, calls the same function for the block's name:

```ts
import {
  blockFormId,
  clearFormStateCookie,
  findForm,
  readFormState,
  renderGravityForm,
} from "@getquick/content/forms/astro";

// In the page's frontmatter: `entry` is the delivered entry (on the home
// page, the delivered `page`), whose `forms` are its forms' descriptors,
// `chrome` its language's chrome, `lang` the page's BCP 47 language (pt-PT).
const workers = await import("cloudflare:workers").catch(() => null);
const siteKey = (workers?.env as { TURNSTILE_SITE_KEY?: string } | undefined)?.TURNSTILE_SITE_KEY;
const formBlock = (block) => {
  const descriptor = findForm(entry.forms, blockFormId(block.attributes) ?? 0);
  const state = descriptor
    ? readFormState({ url: Astro.url, cookie: Astro.request.headers.get("Cookie") }, descriptor.id)
    : null;
  if (state) {
    Astro.response.headers.append(
      "Set-Cookie",
      clearFormStateCookie(state.formId, { secure: Astro.url.protocol === "https:" }),
    );
  }
  return renderGravityForm({
    descriptor,
    source: Astro.url.pathname,
    language: lang,
    legal: chrome?.legal,
    state,
    turnstile: siteKey ? { siteKey } : null,
  });
};
// …then pass `blocks: { "gravityforms/form": formBlock }` when rendering.
```

The form's privacy consent field links to the privacy policy that the page
language's Legal Contract names (`chrome.legal`). The consent is stored with
the Gravity Forms entry. It is not a CONSENT-1 consent decision and writes no
consent record. A page that renders WordPress's `content` HTML instead of its
blocks shows Gravity Forms' own PHP form, which posts to the CMS: render the
blocks instead.

## Turnstile

A Site that lists `"turnstile"` in `forms.spam` needs a Turnstile widget for
the Frontend's hostnames, created in the Cloudflare dashboard, and both of its
keys in Sigillo **staging**, where the Frontend's deploy reads them:

| Name                   | What the deploy binds                                                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TURNSTILE_SECRET_KEY` | A Worker secret. The form route verifies each post's token with it, server-side.                                                                                 |
| `TURNSTILE_SITE_KEY`   | A plain binding, because the key is public. The Site's renderer reads it from the Worker's bindings (`cloudflare:workers`) and passes it to `renderGravityForm`. |

Without either key, `pnpm deploy:frontend` stops before deploying, and
readiness fails. After adding them, run `pnpm ci:deploy` so that CI releases
pass them on too. Turnstile's script loads only when a visitor starts filling
in a form, never with the page (CONSENT-1 CN-R3).

## The CMS's REST gate

The CMS's `web/app/mu-plugins/content-api.php` closes the REST API to anonymous
callers. It makes one exception, for the form route's submissions: an anonymous
request passes only when all of these hold:

- its method is `POST`, with no method override (`?_method=` or
  `X-HTTP-Method-Override`);
- its route is exactly `/gf/v2/forms/<id>/submissions` (`<id>` a positive
  integer; a trailing slash is ignored);
- gq-content's forms module reports Gravity Forms active
  (`GetQuick\Content\Forms\active()`, from gq-content 0.4.0).

Everything else stays `401 rest_auth_required`, including the REST index,
reading a form, its entries and the submission route's validation endpoint.
Gravity Forms then checks the form itself: whether it exists and is active, its
fields, its honeypot and its own spam checks. The exception admits any form's
id, not only the forms published content references: gq-content has no cheap
check for that yet, and narrowing the gate to it is a gq-content follow-up.

`content-api.php` is created once with the CMS, so `gq sync` doesn't update an
existing Site's copy, and `pnpm doctor` fails a Site with `forms` whose copy
still closes submissions. In the existing `rest_authentication_errors` filter,
after the `is_user_logged_in()` check, add:

```php
$forms = function_exists('GetQuick\\Content\\Forms\\active') && \GetQuick\Content\Forms\active();
$post = ($_SERVER['REQUEST_METHOD'] ?? '') === 'POST' && !isset($_GET['_method']) && !isset($_SERVER['HTTP_X_HTTP_METHOD_OVERRIDE']);
$route = $GLOBALS['wp']->query_vars['rest_route'] ?? '';
if ($forms && $post && is_string($route) && preg_match('#^/gf/v2/forms/[1-9][0-9]*/submissions$#D', untrailingslashit($route)) === 1) {
    return $result;
}
```

Then deploy the CMS. Without it, every submission fails with a 401 and the
form route answers that the form couldn't be sent.

## CMS behind Cloudflare Access

The form route posts to Gravity Forms' submissions endpoint
(`POST /wp-json/gf/v2/forms/<id>/submissions`) without a WordPress
credential; [the CMS's REST gate](#the-cmss-rest-gate) lets it through. If the
CMS's Cloudflare Access policy also covers that path, give the Frontend its own
service token for it alone, `GQ_FORMS_ACCESS_CLIENT_ID` and
`GQ_FORMS_ACCESS_CLIENT_SECRET`. Never reuse the GraphQL reader's
([Cloudflare Access for the CMS](cms-access.md)). Put both in the Sigillo
environment the Frontend deploys from, and run `pnpm ci:deploy`. Set both or
neither: the deploy refuses half a pair. A Site whose CMS isn't behind Access
needs neither.

## Readiness

| Command                                         | What it checks                                                                                                                                                                                                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm doctor`                                   | The form route exists (else run `gq sync`). `src/lib/content.ts` passes `forms` (warns if not). The CMS's `content-api.php` lets submissions through. With Turnstile, Sigillo staging has both keys.                                                                    |
| `pnpm site:check:local`                         | With DDEV running, `ddev wp gq-forms status --format=json` must report Gravity Forms active, and every form that published content references free of diagnostics. A CMS without `wp gq-forms` has gq-content older than 0.4.0.                                         |
| `pnpm site:check`                               | The production CMS's WPGraphQL has `getquickForms` (Gravity Forms active, with gq-content 0.4.0). Every form that published content references can be sent (`formsReadiness`). With Turnstile, both keys are present. An Access pair for the submissions path is whole. |
| `wp gq-forms status [--format=json]` on the CMS | Gravity Forms' state, and each referenced form with its diagnostics and the pages that reference it, in every language. Exits 1 while any form has a diagnostic.                                                                                                        |

`pnpm site:check` reads the forms of the content WPGraphQL lists (on a
bilingual Site, the view one GraphQL request returns). `wp gq-forms status` on
the CMS is the complete list. A form that enables no honeypot, on a Site that
lists `"honeypot"`, is a warning, not a failure.

## What the Frontend binds

On a Site with `forms`, `infra/frontend.run.ts` adds these to the Frontend's
Worker:

- `FORMS_RATE_LIMITER`: 10 posts a minute for each form and client IP. The IP
  is used only as the counter's key and is never stored.
- `TURNSTILE_SECRET_KEY` and `TURNSTILE_SITE_KEY`, when the Site chose Turnstile.
- `GQ_FORMS_ACCESS_CLIENT_ID` and `GQ_FORMS_ACCESS_CLIENT_SECRET`, when set.

None of these is a Gravity Forms credential. CI's release step forwards the
optional secrets the same way it forwards the others (`gq ci deploy`).
