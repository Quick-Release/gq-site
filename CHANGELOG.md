# Changelog

All notable changes to `@getquick/site` are recorded here. Versions follow
[Semantic Versioning](https://semver.org/); each release is tagged `v<version>`.

## Unreleased

### Added

- **Protected Sites can hold their deploys.** A `gq.ops.json` `deployment`
  block (`protected: true` with `state` `paused`, `reserved` or `authorized`,
  and a `reason` and `holder` while holding) makes `gq ploi release`,
  `gq release package` and the generated CI release step refuse a paused or
  reserved Site before anything is uploaded, synced or deployed. No flag
  lifts a hold; a reviewed Site change does. A Site without the block deploys
  as before. See [Deployment policy](docs/reference/deployment-policy.md).
  `gq sync` updates `scripts/ci-release.mjs`.
- **Guarded Composer packages.** `deployment.guardedPackages` makes a
  release check the release commit's `deploy/ploi/package-expectations.json`
  (the Site's expectation: version, lock reference, install path and files
  digest) against its `composer.lock`, look up a `phase: "deploy"` approval
  record (`gq-support.composer-approval/v1`) through `run()`'s `approvals`
  adapter, ship the approved file list, and look the record up again, fresh,
  right before changing the Ploi site. The deploy script then verifies the
  installed files (`gq-support.files/v1`) and the lock after
  `composer install`, before PHP-FPM reloads or any WP-CLI or database step.
  gq-site ships no adapter, so a Site guarding a package refuses to prepare or
  deploy it until one is integrated. See
  [Package expectations](docs/reference/package-expectations.md). `gq sync`
  updates `deploy/ploi/admin.sh`; a Site guarding nothing deploys as before.
- **Guarded single-package preparation.** `gq release package` takes
  `--to <version>` (lock exactly that version through Composer's temporary
  `--with` constraint, keeping a requirement that already admits it, and
  refusing one that doesn't), `--pin` (also set the requirement to exactly
  that version), `--reference <ref>`, `--expect-before <version>` and
  `--no-deploy`. The update is lock-only and refuses any other locked
  package's change or any unasked `composer.json` change, restoring both
  Composer files, and `--no-deploy` commits without any provider call.
- **Composer-only deploys from gq.** `gq ploi release --composer-only` (and
  `gq release package --composer-only`) passes `composer_only`, so the deploy
  script stops after Composer and its verifications. Until now only the
  deploy script understood `COMPOSER_ONLY`; no gq command set it.

## 0.29.2 — 2026-10-31

### Fixed

- **A new Site's CMS installs again: its GETQUICK pins resolve together.**
  0.29.0 pinned `getquick/gq-design` exactly at 0.9.4 in both CMS skeletons,
  beside `getquick/getquick-theme` 0.5.1 and (commerce) `getquick/getquick-ecommerce`
  0.3.5, which require `getquick/gq-design ^0.3.1`, so `composer install` in a
  new content or commerce Site's `apps/cms` couldn't resolve. Both skeletons
  now pin `getquick/getquick-theme` 0.6.1 and `getquick/gq-support` 0.1.10,
  and the commerce one `getquick/getquick-ecommerce` 0.4.3; theme 0.6.1 and
  eCommerce 0.4.3 require `getquick/gq-design ^0.9.0`. `getquick/gq-config`
  stays 0.4.3 (theme 0.6.1 accepts `>=0.4.0 <1.0`): 0.5.1 adds a server-side
  password policy that would send the local `dev`/`dev` admin to its Profile
  on every wp-admin login, a change a patch release doesn't make. Both
  generated skeletons resolve against the registry, and on WordPress 7.1.3
  `admin.sh`'s steps activate every `wordpress.plugins` entry and
  `getquick-theme`, gq-config loads, and eCommerce 0.4.3 boots on GQ Design
  0.9.4 and registers the storefront's `getquick-config/v1/woocommerce/auth/*`
  routes. It still reads `GETQUICK_STOREFRONT_PROXY_SECRET`, and its auth
  contract is still 0.1.9, which `@quick-release/storefront` 0.2.2 uses.
  A Site's `apps/cms/composer.json` is its own once created, so a Site
  generated by 0.29.0 or 0.29.1 sets those pins itself and runs
  `pnpm cms:composer:update getquick/getquick-theme getquick/gq-support getquick/gq-design`
  (commerce: also `getquick/getquick-ecommerce`).
- **Pins Composer can't install together fail the package suite, offline.**
  `blueprint/package-requirements.json` records what each pinned GETQUICK
  package's pinned version requires of the others, from the registry's
  metadata, and the catalogue check refuses a pin that a recorded
  requirement excludes, a pin moved without its record, and a GETQUICK
  requirement neither skeleton pins. The catalogue now reads the commerce CMS
  skeleton too (`variantComposerFiles`), catalogues `getquick/getquick-ecommerce`,
  and requires each skeleton to pin its variant's packages, at one pin.
  `gq packages check` fails when a record differs from the registry
  (`requirements-drift`), `gq packages propose` holds a move that a pinned
  package's requirement excludes (`unsatisfied`, with its lockstep group:
  GQ Design 0.10.0 while getquick-theme requires `^0.9.0`), and `--write`
  edits both skeletons and the records. An exact pin under `manual` policy is
  reported as `manual` instead of `unsupported-constraint`.
  `scripts/smoke/cms-resolve.sh` resolves both generated skeletons with
  `composer update --dry-run` against the registry and checks each GETQUICK
  package locks at its pin; CI runs it when the repository has a
  `COMPOSER_AUTH` secret, and otherwise skips it with a warning.

## 0.29.1 — 2026-10-31

### Fixed

- **A new commerce Site passes its own root `vp fmt --check`.** In a commerce
  Site generated by 0.29.0, the formatter rewrapped the managed
  `infra/storefront-bindings.ts` and `infra/scripts/deploy-frontend.mjs`, so

  formatter orders it. Those three are the Site's own once created: a Site
  generated by 0.29.0 runs `pnpm exec vp fmt --write apps/frontend` once.
  Content Sites, Astro and TanStack, already passed and are unchanged. The
  formatter-stability suite now generates every variant and framework and
  runs the Site's root `vp fmt --check`, offline, and the generated-site
  smokes run it after installing.

## 0.29.0 — 2026-10-30

### Added

- **A commerce Site's Frontend mounts the storefront Runtime**
  ([#89](https://github.com/Quick-Release/gq-site/issues/89) slice 6). The
  commerce skeleton depends on `@quick-release/storefront` 0.2.2 and
  `@quick-release/auth-contract` 0.1.9 (GitHub Packages, pinned exactly,
  nothing from Ekis), configures the Runtime from `gq.ops.json` in
  `src/storefront.server.ts`, mounts it at `/api/auth/*` and `/api/store/*`,
  and gives the router the Runtime's Query client. Installing a generated
  commerce Site therefore needs a `read:packages` token; generating one
  doesn't. The commerce CI Worker (its own `infra/ci/cloudflare.ci.ts` and
  `env.ts`) writes `GITHUB_PACKAGES_TOKEN` to the install container's
  user-level npm config, refusing without it, and hands the storefront's
  secrets to the Frontend's deploy. A Site generated by 0.28.0 adds the same
  by hand: [Add the storefront Runtime](docs/guides/storefront-runtime.md).
  Content Sites' files are unchanged. A commerce Site still has no readiness
  ([#26](https://github.com/Quick-Release/gq-site/issues/26)).

- **GQ Design is pinned as one lockstep group**
  ([#93](https://github.com/Quick-Release/gq-site/issues/93),
  [ADR 0018](docs/adr/0018-ship-gq-designs-contract-and-renderer-as-lockstep-packages.md)).
  `getquick/gq-design` is pinned exactly at `0.9.4` in both CMS skeletons
  (was `*@stable`), and a commerce Frontend's managed keys pin
  `@quick-release/design-contract` and `@quick-release/design-renderer` at
  the same version, so `gq sync` adds them to a commerce Site's
  `apps/frontend/package.json` (run `pnpm install` afterwards). The package
  catalogue gains npm packages (`ecosystem: "npm"`, discovered on GitHub
  Packages with `GITHUB_PACKAGES_TOKEN` or the user's npm config), the
  `exact` policy and `lockstep` groups: `gq packages check` reports the
  newest version every member's registry serves and names a lagging member,
  and `gq packages propose` moves the whole group or none of it. `gq doctor`
  fails a Site whose `composer.lock` and `pnpm-lock.yaml` lock GQ Design at
  different versions, naming both; a content Site, which locks no design
  package, passes. No renderer adapter is generated yet.

### Fixed

- A commerce deploy before provisioning names the missing
  `gq.ops.json domains.admin` instead of crashing.

## 0.27.0 — 2026-10-30

### Added

- **Agent access to production CMS content**
  ([#137](https://github.com/Quick-Release/gq-site/issues/137),
  [gq-platform ADR 0011](https://github.com/Quick-Release/gq-platform/blob/main/docs/adr/0011-agent-access-to-production-cms-content.md)).
  `gq content get|diff|validate|put` read and write one page's or post's raw
  block markup over REST, as the Site's agent user (an Editor, by an
  application password) behind Cloudflare Access: with the agent's service
  token or a person's `cloudflared access login` session. `get` writes
  `content.raw` or its parsed block tree (`.json`), which is what an edit
  changes; `validate` writes the result to the same post in the Site's DDEV
  CMS and fails if KSES changes it or the block editor (in a headless Chrome)
  marks any block invalid or unregistered; `put` refuses bytes that didn't
  pass `validate` and a post changed since `get`, writes once and confirms
  the new revision, the rollback. The Sigillo names `GQ_CMS_AGENT_USERNAME`,
  `GQ_CMS_AGENT_APPLICATION_PASSWORD`, `GQ_CMS_AGENT_ACCESS_CLIENT_ID` and
  `GQ_CMS_AGENT_ACCESS_CLIENT_SECRET` go only to the configured CMS origin
  and the page, post and revision routes, never through a redirect.
  `gq wp` is break-glass WP-CLI: the host comes from `gq.ops.json` or Ploi,
  the command runs as a Ploi one-off script from an allowlist (no raw SQL,
  PHP or bulk or destructive commands), and a write runs `gq db backup`
  first; `post update <id> <file>` confirms the stored bytes and the new
  revision. `scripts/smoke/cms-content.sh` proves the route on a real
  WordPress. See
  [Agent access to production CMS content](docs/guides/cms-content.md).

## 0.26.0 — 2026-10-29

### Added

- **A Frontend behind an external proxy**
  ([#134](https://github.com/Quick-Release/gq-site/issues/134)). The new
  optional `gq.ops.json` key `domains.frontendProxy` (with
  `domains.frontendTarget`) says that a reverse proxy we run outside
  Cloudflare serves `domains.frontend`, with a certificate of its own, and
  forwards to `frontendTarget`, with `Host` and SNI `frontendTarget`. Use
  it when the client requires a certificate authority Cloudflare can't serve.
  The production Frontend deploy (Astro and TanStack) then gives the Worker
  the Custom Domain `frontendTarget` and no Cloudflare for SaaS route.
  `domains.frontend` stays the public, canonical origin.
  `frontendProxy.trustedProxies` lists the proxy's addresses (IPv4 or IPv6,
  or CIDRs). The production Worker gets them as `GQ_TRUSTED_PROXIES`, and the
  form and consent routes pass them to `@getquick/content` as
  `trustedProxies`.
  `gq cloudflare custom-hostname` refuses such a Site and says why. `gq
offboard` cuts no route for it, and lists the proxy and the public
  hostname's DNS as manual steps. See
  [A Frontend behind an external proxy](docs/guides/provisioning.md#a-frontend-behind-an-external-proxy).

### Changed

- The content package pair moves to **0.4.2** (`getquick/gq-content` and
  `@getquick/content`, tag `v0.4.2`). It adds `trustedProxies` to
  `createFormsServer` and `createConsentServer`, and its rate limits key an
  IPv6 visitor by its /64. See
  [0.4.0 to 0.4.2](docs/guides/content-pair-migration.md#040-to-042-getquicksite-0260).

### Fixed

- The managed `/gq/forms/` and `/gq/consent` routes pass `siteOrigins` (the
  origins of `domains.frontend` and `domains.frontendTarget`) to
  `@getquick/content`. Behind an external proxy, a browser's post from the
  public hostname is then the Site's own, not a cross-site 403. A TanStack
  Site's consent handler is in `apps/frontend/src/site.server.ts`, which `gq
sync` creates once and doesn't update: an existing TanStack Site adds
  `siteOrigins` and `trustedProxies` to its `createConsentServer` call by hand.

## 0.25.0 — 2026-10-27

### Added

- **A Frontend on the client's own domain**
  ([#131](https://github.com/Quick-Release/gq-site/issues/131)). The new
  optional `gq.ops.json` key `domains.frontendTarget` says that
  `domains.frontend` is outside the Cloudflare zone and is served as a
  Cloudflare for SaaS custom hostname. It names the Frontend's hostname in
  the zone, which the public one CNAMEs to. `domains.frontend` stays the
  public, canonical hostname everywhere it is read. The production
  Frontend deploy (`infra/frontend.run.ts`, Astro and TanStack) keeps its
  Custom Domain on `frontendTarget` and adds the route
  `<domains.frontend>/*` on the zone.
- `gq cloudflare custom-hostname [--dry-run]` creates the custom
  hostname: TXT ownership pre-validation and a DV certificate that
  delegated DCV renews. It then prints the DNS records the client adds:
  the ownership TXT, the `_acme-challenge` CNAME and the traffic CNAME.
  `gq cloudflare custom-hostname status [--json]` checks the fallback
  origin, the hostname, its certificate, the route, the client's CNAME and
  their CAA records (`letsencrypt.org`, `pki.goog`, `ssl.com` must be
  allowed), and exits 1 until all are right. Enabling Cloudflare for SaaS
  and setting the fallback origin are done once per zone, by hand, and
  never to a Site's own Frontend host: both commands say when the fallback
  origin is missing or is this Site's. See
  [A Frontend on the client's own domain](docs/guides/provisioning.md#a-frontend-on-the-clients-own-domain).

- **TanStack Start Frontends**
  ([#130](https://github.com/Quick-Release/gq-site/pull/130)). The new
  optional `gq.ops.json` key `framework` (`"astro"` or `"tanstack"`) picks
  the Frontend's framework, separately from `variant`. Left out, it is
  `"astro"`, so existing Sites keep Astro. A TanStack content Frontend
  needs `contentRuntime: "package"`. `gq sync` manages its `/gq` route
  adapters (events, refresh, consent and, with `forms`, forms), and the
  production deploy uses Alchemy's `Cloudflare.Website.Vite`, with the
  same Stack, D1 and consent identities as Astro. `gq doctor` and
  `gq site check` give advice that fits the framework.
  `scripts/smoke/tanstack-check.mjs` builds and runs a generated TanStack
  Frontend in workerd, in CI. See
  [Frontend frameworks](docs/reference/frontend-frameworks.md).

### Changed

- `gq new` creates TanStack Start Frontends by default. `--framework astro`
  still creates the Astro skeleton. Existing Sites aren't migrated: changing
  `framework` means replacing the Site's own app.
- `gq offboard` removes a custom hostname's route and records it in
  `offboarded.cut.workerRoutes`, and `--restore` adds it back. The custom
  hostname itself stays on the zone. `gq offboard --archive` deletes DNS
  records at `domains.frontendTarget` instead of `domains.frontend`, and
  lists deleting the custom hostname as a manual step. While a Site is
  offboarded, `gq cloudflare custom-hostname` refuses to run; its `status`
  still works.

## 0.24.1 — 2026-10-26

### Fixed

- **Form submissions reach Gravity Forms.** The CMS's `content-api.php`
  closed the whole REST API to anonymous callers, so every post from the
  `/gq/forms/` route failed with `401 rest_auth_required`. Its gate now lets

  `content-api.php` is created once, so `gq sync` doesn't change an existing

  `gq doctor` fails one whose copy still closes submissions.

### Added

- `scripts/smoke/cms-rest-gate.sh`, run in CI: the generated `content-api.php`
  on a real WordPress over HTTP, with stand-ins for Gravity Forms' routes and
  gq-content's forms module.

## 0.24.0 — 2026-10-26

### Added

- **Headless Gravity Forms**
  ([gq-platform ADR 0009](https://github.com/Quick-Release/gq-platform/blob/main/docs/adr/0009-headless-gravity-forms.md)).
  The optional `gq.ops.json` key `forms` (`provider: "gravityforms"`, `spam`:
  `"honeypot"` and/or `"turnstile"`) needs `contentRuntime: "package"` and
  `gravityforms` in `wordpress.plugins`. With it, `gq sync` manages
  `apps/frontend/src/pages/gq/forms/[...rest].ts`, which hands
  `POST /gq/forms/<id>` to `@getquick/content/forms/server`'s
  `createFormsServer`, using the descriptor published with the posting page.
  Without the key, sync writes no form route, and it removes one it wrote that
  the Site hasn't edited. The managed route holds no form logic. New Sites'
  `src/lib/content.ts` passes `forms: Boolean(manifest.forms)`; existing Sites
  add `forms: true` themselves. Rendering the `gravityforms/form` block stays
  Site-owned: see [Headless Gravity Forms](docs/guides/forms.md).
- The Frontend deploy binds `FORMS_RATE_LIMITER` on a Site with forms. When
  the Site chose Turnstile, it also binds `TURNSTILE_SECRET_KEY` (a secret) and
  `TURNSTILE_SITE_KEY` (plain) from Sigillo staging, and refuses to deploy
  without them. An optional `GQ_FORMS_ACCESS_CLIENT_ID` and
  `GQ_FORMS_ACCESS_CLIENT_SECRET` pair serves a CMS whose submissions path is
  behind Cloudflare Access; half a pair is refused. CI forwards all four.
- Readiness adds a `forms` area to `gq site check`. `gravity-forms` checks
  that the CMS's WPGraphQL has gq-content's `getquickForms`. `form-fields`
  checks every form that published content references with `formsReadiness`.
  `spam-controls` checks Turnstile's keys, and `cms-access` checks the Access
  pair. `gq site check --local` runs `wp gq-forms status --format=json` in
  DDEV. `gq doctor` checks the form route, the runtime opt-in and Turnstile's
  keys in Sigillo staging.

### Changed

- Pin `@getquick/content` and `getquick/gq-content` to the 0.4.0 pair, which
  adds the forms capability. Nothing changes for a Site that doesn't opt in.
  Existing package-runtime Sites upgrade `@getquick/site`, run `gq sync`,
  install both halves, and commit both lockfiles
  ([0.3.2 to 0.4.0](docs/guides/content-pair-migration.md#032-to-040-getquicksite-0240)).

## 0.23.0 — 2026-10-23

### Added

- **Optional trusted private Site preview bindings** ([#122](https://github.com/Quick-Release/gq-site/pull/122)).
  The manifest accepts HTTPS `preview.cmsUrl` and `preview.audience`, and the
  new `@getquick/site/preview-bindings` export validates them before deployment.

  password pair; an optional Access service pair adds gateway authentication.

human review or public-delivery acceptance (Design issues 66/67).

  `gq new` (or `gq sync`) when absent and recorded in the lock as created
  once present, so they are never rewritten or restored after.
  `gq sync --recreate <path>` writes one again.
- The site's deploy wiring, fully generated from `gq.ops.json` and
  extracted from an existing content site: the Cloudflare CI Worker (`infra/ci`: Wrangler
  config, CI and mirror Workflows, webhook, release check, sandbox image),
  the Frontend deploy configuration and script (`infra/frontend.run.ts`,
  `infra/scripts/deploy-frontend.mjs`, `infra/package.json`), the CI release
  step (`scripts/ci-release.mjs`) and their tests (`scripts/ci.test.mjs`).
  Worker, Workflow, namespace, bucket, account and repository names come
  from `ci`, `artifacts`, `cloudflare` and `github`, the rest from
  `project`; a value the manifest doesn't have yet is written as a
  placeholder naming its key (`<ci.worker>`). The content-site fixture's
  manifest renders that site's files byte for byte.
- Managed root scripts for the deploy wiring: `deploy:frontend`,
  `deploy:frontend:raw` (the release step's Frontend deploy),
  `plan:frontend`, `infra:check`, `ci:check` and `test:scripts` (checks the
  content variant's `gq verify` runs).
- The CMS deploy script Ploi runs (`deploy/ploi/admin.sh`), fully generated
  and extracted from an existing content site: release download, Composer with the registry
  login, the copy-back of shipped plugins and themes, maintenance mode, the
  PHP-FPM reload and the `<PROJECT>_DEPLOY_STATUS` line. It activates the
  plugins `wordpress.plugins` lists, in order, then runs the site's deploy
  extensions (`deploy/ploi/admin.d/*.sh`, created once with a README) in
  lexical order; one that exits non-zero fails the deploy. The content-site
  fixture's manifest renders that site's script without its own steps (its
  theme, the plugin retirements and the clean-up of its git-based deploys),
  which belong in an extension.
- `gq new` writes a complete content site: create-once CMS and Frontend
  skeletons extracted from an existing content site without its plugins,
  child theme and pages (the CMS installs the GETQUICK plugins and `getquick-theme` from the
  registry, a `10-theme.sh` deploy extension activates the theme, and the
  Frontend renders GETQUICK blocks over WPGraphQL with its own copy of
  the block renderer), env templates holding public configuration and
  placeholders only, the workspace config (`pnpm-workspace.yaml`),
  `VERSION`, and a root `package.json` started with the site's own scripts
  and dependencies (`@getquick/site` pinned to the installed version). Its
  `gq.ops.json` lists the skeleton's plugins in `wordpress.plugins`. A
  generated site passes `pnpm verify`.
- `gq new` asks for the directory, project or variant it is missing when
  run in a terminal, and names them otherwise. It then prints the
  provisioning sequence (`ploi provision`, `cloudflare …`, `github setup`,
  `ci deploy`), running none of it.
- An app skeleton's create-once files are written only with their app:
  `gq sync` creates them while the app's directory (`apps/cms`,
  `apps/frontend`) is missing, never into an app the site already has.

### Changed

- `gq new` refuses a project name that isn't lowercase letters, digits and
  hyphens starting with a letter, since it names packages, Workers and the
  DDEV project, and an unknown `--variant`.
- `wordpress.plugins` in `gq.ops.json` takes plugin slugs only (letters,
  digits, `-`, `_` and `.`, starting with a letter or digit), since the
  deploy script activates each one.
- `gq.lock.json` also records a hash for each generated section
  (`sections`) and managed key (`keys`), and the create-once files it has
  created (`created`). A lock from 0.11.0 is upgraded on the next sync. An
  edit inside a section, or to a managed key, stops `gq sync` with a diff of
  the whole file, like an edited managed file.
- `gq sync` manages symlinks and executable files. A retargeted symlink, or
  anything else standing in its place, is a local edit, shown as a diff of
  the targets. A managed file that lost its executable bit is made
  executable again rather than taken for an edit.
